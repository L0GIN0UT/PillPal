# PillPal — техническое задание

> Версия 1.0 · 16.10.2026 · составлено по итогам интервью с владельцем продукта (Ivan, L0GIN0UT)

PillPal — тёплое и простое напоминание о лекарствах для себя и близких: расписания, которые различаются по дням, отметки о приёме и спокойствие за родных без звонков «ты выпил таблетку?». Ядро бесплатно, без пробного периода и обязательной подписки; реклама отключается разовой покупкой.

---

## 1. Ключевые решения

| Область | Решение |
|---|---|
| Цель | Коммерческий продукт; первые пользователи — семья автора (dogfooding) |
| Рынок | Глобально; языки RU + EN (i18n с первого дня) |
| Платформы | iOS + Android, Flutter. Веба нет |
| Магазины | Google Play, App Store, RuStore, Xiaomi GetApps, Samsung Galaxy Store |
| Бэкенд | Python 3.12, FastAPI, PostgreSQL 16, Redis (+ ARQ для отложенных задач) |
| Регионы данных | Два независимых стенда сразу: **RU** (152-ФЗ, данные граждан РФ только в РФ) и **EU** (GDPR). Регион определяется автоматически (локаль/IP) и подтверждается при регистрации; смена — через экспорт/импорт |
| Межрегиональные связи | **Запрещены на старте** (близкие — только внутри одного региона) |
| Вход | Аккаунт обязателен с первого запуска. RU-Android: email+пароль, VK ID, Яндекс ID. RU-iOS: только email+пароль. Остальной мир: email+пароль, Apple, Google |
| Офлайн | Offline-first: напоминания локальные, синк при появлении сети |
| Публикация | Пока физлицо, без платежей. Бэкенд оплаты есть, но выключен флагом |
| Реклама | Yandex Ads + медиация; сеть/юниты выбираются серверным конфигом по региону. Только баннеры на вторичных экранах; **никогда** на экране напоминания и отметки приёма |
| Монетизация | Разовая покупка «убрать рекламу» (под флагом). Мягкие лимиты (число близких ≈3, число PDF-отчётов) — под флагом, включаются вместе с оплатой |
| Аналитика | AppMetrica + self-hosted Sentry по регионам. Никаких медданных в событиях |
| Процесс | Монорепо, TDD, GitHub Actions, агенты everything-claude-code, адаптированные под Flutter + FastAPI |
| Дизайн | Сначала дизайн-система и макеты ключевых экранов → ревью владельцем → UI-код |

## 2. Функциональные требования

### 2.1 Лекарства
- Ввод: **свободный** (название, форма, дозировка, заметка «после еды»), **из справочника** (автодополнение), **скан упаковки** (EAN-13 / UPC-A / DataMatrix «Честного знака»).
- **Модель препарата — 4 уровня**: Вещество (МНН/INN) → Состав (набор «вещество + дозировка» + лекарственная форма) → Продукт (торговое название, страна, производитель) → Упаковка (GTIN, количество). Идентичность препарата = полный состав + форма (Терафлю ≠ Фервекс).
- Источники справочника: РФ — ЕСКЛП/ГРЛС (проверить лицензию), США — RxNorm Prescribable / openFDA NDC (CC0), ЕС — EMA; плюс пользовательские связки GTIN.
- GTIN нормализуется к GTIN-14. Коды ограниченного обращения (префиксы 02, 20–29) в общую базу не попадают. Один продукт может иметь несколько GTIN.
- Связка «GTIN → продукт» создаётся только выбором продукта из справочника; становится общей после N совпадающих подтверждений, спорные — в админке. Ручной состав остаётся личным.
- При добавлении: тот же состав → предложить привязать упаковку к существующему лекарству; пересечение веществ → информационная подсказка «оба содержат X» (без медицинских выводов); всегда можно создать отдельно.
- Каталог GTIN/справочник — глобальный сервис без персональных данных.
- Приватность на лекарство: `shared` (видно близким) / `anonymous` (видно «приём в 20:00 ✔» без названия) / `hidden`.

### 2.2 Расписания
- Типы: ежедневно в фиксированное время (одно или несколько), по дням недели, каждые N дней, курс (дата начала/окончания), разные дозы в разное время, разные дозы в разные дни (несколько расписаний на одно лекарство), «по необходимости» (без напоминаний, только отметка).
- Не в первом релизе: циклы (21/7), титрование.
- Часовые пояса: по умолчанию время приёма — по **местному** времени устройства; для отдельного лекарства можно закрепить исходный пояс (интервалы строго соблюдаются).
- Формальная спецификация — `docs/spec/schedule.md` + общие тест-векторы `spec/schedule-vectors/`.

### 2.3 Напоминания
- Уровни настраиваются пользователем (глобально и на лекарство): тихое → обычное → настойчивое (повторы каждые N минут до отметки, max M раз) → режим будильника (iOS 26+ AlarmKit, Android — канал будильника, exact alarms).
- Android: `SCHEDULE_EXACT_ALARM` с запросом у пользователя, деградация до неточных; перепланирование после перезагрузки; онбординг про оптимизацию батареи (Xiaomi/Huawei/Samsung).
- iOS: Time Sensitive; скользящее окно ≤ 64 запланированных уведомлений, пересчёт при запуске/фоновом обновлении.
- Действия прямо из уведомления: «Принял», «Отложить», «Пропустить».

### 2.4 Отметки и история
- События приёма — неизменяемые (append-only): `taken`, `skipped`, `snoozed`, `undo`.
- Календарь истории, процент соблюдения, PDF-отчёт для врача за период.
- Учёт остатка (опционально): списание при отметке, «осталось на N дней», кнопка-диплинк «Аптеки рядом» в картах устройства (Яндекс/Google/Apple Maps). Своей карты нет.

### 2.5 Близкие
- Симметричная модель: у каждого свой аккаунт; владелец выдаёт близкому право `view` или `view+edit` на свой профиль.
- Подопечные профили (бабушка без смартфона, ребёнок, питомец): ведутся аккаунтом-опекуном, напоминания приходят опекунам.
- Приглашение: ссылка + QR; приглашённый подтверждает.
- Пропуск: повторы → через X минут (по умолчанию 30, настраивается) пуш близким. Детект пропуска — на сервере по расписанию.

### 2.6 Прочее
- Режим для старших (крупный шрифт и кнопки, повышенный контраст), тёмная тема, виджет на домашний экран.
- Удаление аккаунта и экспорт данных (требование сторов и законов).
- Шифрование: TLS + шифрование на диске; E2E нет (серверу нужно расписание для детекта пропусков).

## 3. Нефункциональные требования
- Напоминание срабатывает без сети и после перезагрузки; потеря сети не ломает отметки.
- Синк идемпотентен: повтор запроса не создаёт дублей.
- Персональные данные пользователя хранятся только в базе его региона. Медданные никогда не попадают в логи, аналитику, Sentry.
- Пароли — Argon2id; access-JWT 15 мин; refresh-токены одноразовые с ротацией и детектом повторного использования.
- Логи структурированные (JSON) с request-id; health/readiness эндпоинты; RED-метрики.
- Покрытие: доменная логика (расписания, синк, авторизация) — обязательные тесты; CI блокирует merge при падении.

## 4. Архитектура

```
PillPal/
├── app/                      # Flutter-приложение (фаза 2)
├── packages/pillpal_core/    # чистый Dart: модели, движок расписаний (фаза 1)
├── backend/                  # FastAPI-сервис (один код, деплой per region)
├── spec/schedule-vectors/    # общие JSON-тест-векторы для Python и Dart
├── infra/                    # docker-compose, Dockerfile, nginx
├── docs/                     # ТЗ, спецификации, ADR
└── .claude/                  # агенты, правила, команды (адаптация ECC)
```

### 4.1 Модель данных (ядро, фаза 1)
- `users` (id, email, password_hash, region, locale, created_at, deleted_at)
- `profiles` (id, owner_user_id, kind: `self`|`managed`, display_name, timezone) — у каждого пользователя автоматически создаётся профиль `self`.
- `medications` (id, profile_id, name, form, strength_text, notes, tz_mode: `local`|`fixed`, fixed_tz, stock_count, stock_unit, low_stock_days, privacy, version, updated_at, deleted_at)
- `schedules` (id, medication_id, rule JSONB — см. §4.2, version, updated_at, deleted_at)
- `dose_events` (id, profile_id, medication_id, occurrence_key, type, at, recorded_at, device_id, note) — append-only.
- `sync_changes` (seq BIGSERIAL, user_id, entity, entity_id, op) — журнал изменений для pull.
- `refresh_tokens`, `devices`.

Все id — UUID, генерируются клиентом (офлайн-создание).

### 4.2 Правило расписания (rule, версия 1)
```json
{
  "v": 1,
  "kind": "daily | weekdays | interval_days | as_needed",
  "start_date": "2026-10-16",
  "end_date": null,
  "weekdays": [1, 3, 5],
  "interval_days": 2,
  "times": [
    {"time": "08:00", "dose": {"amount": "1", "unit": "tablet"}},
    {"time": "20:00", "dose": {"amount": "0.5", "unit": "tablet"}}
  ]
}
```
- `weekdays` — ISO (Пн=1 … Вс=7), только для `weekdays`. `interval_days ≥ 2`, якорь — `start_date`. `as_needed` — `times` пустой, вхождений нет.
- **Вхождение** (occurrence) детерминировано: ключ `"{schedule_id}/{YYYY-MM-DD}T{HH:MM}"` (локальная дата и время по правилу). Отметки ссылаются на ключ — поэтому клиент и сервер независимо вычисляют одно и то же.
- Часовой пояс: `tz_mode=local` → время интерпретируется в текущем поясе пользователя; `fixed` → в `fixed_tz`.
- DST: несуществующее время (переход вперёд) сдвигается вперёд на величину разрыва; неоднозначное (переход назад) — берётся первое вхождение.

### 4.3 Синк
- `POST /v1/sync/push` — пакет мутаций `{entity, op: upsert|delete, id, data, client_updated_at}`. Изменяемые сущности (лекарства, расписания) — last-write-wins по `client_updated_at` (тай-брейк — id устройства); удаление — tombstone. События приёма — вставка, идемпотентная по `id`.
- `POST /v1/sync/pull` — изменения по каждому доступному профилю (свой, подопечные, профили близких) после его курсора, постранично; ответ содержит список доступных профилей с ролью и новыми курсорами, а также отозванные профили. Данные близких отдаются с учётом приватности лекарств (фаза 3, ADR 0006).
- Повтор push безопасен.

## 5. Фазы

### Фаза 1 — Фундамент и ядро *(текущая)*
1. Монорепо, `.claude/` (агенты/правила/команды ECC под Flutter + FastAPI), `CLAUDE.md`.
2. CI (GitHub Actions): backend — ruff, mypy, pytest на PostgreSQL-сервисе, сборка Docker-образа; core — `dart analyze`, `dart test`; проверка тест-векторов. CD: публикация образа бэкенда в GHCR на `main`.
3. Бэкенд: конфиг по региону, health/ready, структурные логи, request-id, регистрация/вход email+пароль, refresh-ротация, профили, CRUD лекарств и расписаний (с валидацией правила), события приёма, push/pull синк, Alembic-миграции, тесты на реальной БД.
4. Движок расписаний: спецификация, ≥ 30 тест-векторов (включая DST, смену пояса, курсы, интервалы), эталон на Python (бэкенд), реализация на Dart (`pillpal_core`), обе прогоняются против одних векторов.
5. Дизайн-система и макеты ключевых экранов (Сегодня, Лекарство, Расписание, Близкие, История, Уведомление) — на ревью владельцу.

**Приёмка:** все тесты зелёные локально/в CI; `docker compose up` поднимает бэкенд; OpenAPI доступен; векторы проходят в обеих реализациях; макеты опубликованы.

### Фаза 2 — Приложение (офлайн-ядро)
Flutter-оболочка по утверждённым макетам; локальная БД (drift); синк-клиент; онбординг и вход; лекарства (свободный ввод); расписания всех типов; экран «Сегодня»; уведомления всех уровней с действиями, скользящее окно iOS, exact alarms, перезагрузка; история-календарь, процент соблюдения, PDF; остаток + диплинк аптек; RU/EN; тёмная тема; режим для старших; виджет. Тесты: unit + widget + integration (эмулятор в CI). CD: сборка APK/IPA (Fastlane), внутренние треки.

### Фаза 3 — Близкие
Связи и права, приглашения (ссылка + QR, deep links), подопечные профили, приватность на лекарство, серверный детектор пропусков (ARQ) + пуши FCM/APNs (+ RuStore Push для устройств без GMS), лимиты под флагом.

### Фаза 4 — Справочник и скан
4-уровневая модель препаратов; импортеры RxNorm/openFDA, ЕСКЛП, EMA; глобальный сервис поиска; нормализация GTIN; сканер (EAN/UPC/DataMatrix GS1); консенсус + админка; логика аналогов и пересечения веществ.

### Фаза 5 — Регионы, вход, монетизация, запуск
Деплой RU и EU стендов (IaC), региональный роутинг клиента; OAuth: VK ID, Яндекс ID, Apple, Google — по региону и платформе; Yandex Ads + медиация через remote config; бэкенд оплаты (RuStore Pay, StoreKit, Play Billing) под флагом; AppMetrica + Sentry; удаление/экспорт данных; юридические документы (согласие на обработку медданных отдельным документом, политика, уведомление РКН, GDPR-представитель); публикация во все 5 магазинов.

## 6. Риски и открытые вопросы
- **Apple 5.1.1(ix):** health-приложения должны подаваться юрлицом — публикация от физлица может быть отклонена.
- **Оплата:** AdMob и биллинг Google Play/App Store недоступны разработчику из РФ; для глобальной оплаты нужно зарубежное юрлицо.
- **ЕСКЛП/ГРЛС:** лицензия на коммерческое использование выгрузки не подтверждена.
- **Android exact alarms:** `USE_EXACT_ALARM` для лекарств — риск отказа Google Play; используем `SCHEDULE_EXACT_ALARM`.
- **Критические алерты iOS** для лекарств Apple не выдаёт; AlarmKit (iOS 26) — проверить на ревью.
- **OCR кириллицы** на устройстве (ML Kit) недоступен — OCR не делаем.
- **Сборка Flutter в среде Claude** недоступна (заблокированы storage.googleapis.com и pub.dev) — Dart-код проверяется только в CI.
